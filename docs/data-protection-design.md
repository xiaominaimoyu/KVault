# 本地数据保护设计

> 本文档描述 KVault 本地数据的敏感信息加密存储与知识库级访问保护方案。
> 本任务仅输出设计文档，不实现代码。

---

## 1. 敏感信息加密存储方案

### 1.1 加密候选算法

| 候选 | 类型 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|---------|
| **Fernet**（cryptography 库） | 对称加密（AES-128-CBC + HMAC-SHA256） | API 简单，自带完整性校验，Python 生态成熟 | 密钥需自行管理；AES-128 而非 256 | 文档元数据字段级加密 |
| **AES-GCM**（cryptography 库） | 认证加密（AES-256 + GMAC） | 强安全性，NIST 推荐，支持关联数据（AAD） | API 较底层，需自行管理 nonce | 整文件加密，高安全需求 |
| **OS 密钥环**（keyring 库） | 系统级密钥存储 | 密钥由 OS 安全管理（Windows DPAPI / macOS Keychain），无需明文落盘 | 跨平台行为不一致；依赖系统服务 | 存储主密钥，非数据加密本身 |

### 1.2 推荐方案：Fernet + OS 密钥环

```
加密架构：
┌─────────────┐     ┌──────────────┐     ┌─────────────────┐
│  明文字段    │ →→→ │  Fernet 加密  │ →→→ │  密文存入 SQLite │
└─────────────┘     └──────────────┘     └─────────────────┘
                           ↑
                    ┌──────────────┐
                    │  Master Key  │
                    └──────────────┘
                           ↑
                    ┌──────────────────────┐
                    │  OS 密钥环 (keyring)  │
                    │  Windows DPAPI       │
                    └──────────────────────┘
```

- **主密钥**：256 位 Fernet 密钥，存储在 OS 密钥环中（`keyring.set_password("kvault", "master_key", key)`）
- **首次启动**：自动生成主密钥并存入密钥环；若密钥环不可用，降级到 `data/keys/master.key`（权限 600）
- **加密字段**：在 `config.json` 中标记需加密的字段路径（如 `documents.tags`、`documents.partition_name`）
- **透明加解密**：`MetadataManager` 在写入/读取标记字段时自动加解密

### 1.3 密钥管理

| 项目 | 说明 |
|------|------|
| 密钥文件路径 | `data/keys/master.key`（仅密钥环不可用时使用） |
| 文件权限 | 600（仅所有者可读写，Linux/macOS `chmod 600`；Windows ACL 限制当前用户） |
| 密钥轮换 | 提供 `scripts/rotate_key.py`：解密全部标记字段 → 生成新密钥 → 重新加密 |
| 密钥备份 | 主密钥应由用户自行安全备份（如导出到加密 USB），丢失后数据不可恢复 |

## 2. 知识库级访问保护方案

### 2.1 口令保护

| 候选 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **bcrypt** | 自适应哈希，工业标准 | 抗暴力破解，可调 cost factor | 仅哈希验证，不加密数据 |
| **argon2** | Argon2id（密码哈希竞赛冠军） | 抗 GPU/ASIC 攻击，可调内存/时间参数 | 库安装较重（`argon2-cffi`） |

**推荐**：argon2（若安装方便）或 bcrypt（更轻量）

**机制**：
- 创建工作区时可选设置口令
- 口令哈希存储在 `config.json` 的 `workspaces.items[].password_hash`
- 切换到受保护工作区时弹出口令输入框，验证通过后才加载该工作区数据
- 口令不加密数据本身，仅控制访问入口

### 2.2 加密容器候选

| 候选 | 类型 | 优点 | 缺点 | 成熟度 |
|------|------|------|------|--------|
| **SQLite SEE** | SQLite 官方加密扩展 | 透明加密，API 不变 | 商业付费 | 高（官方） |
| **SQLCipher** | SQLite 开源加密分支 | 免费，广泛使用，社区活跃 | 需替换 SQLite 驱动（`pysqlcipher3`） | 高（社区） |
| **VeraCrypt** | 磁盘级加密容器 | OS 级加密，极强安全 | 手动挂载/卸载，用户体验差 | 高（独立工具） |

### 2.3 方案权衡

| 方案 | 安全强度 | 实现复杂度 | 用户体验 | 推荐阶段 |
|------|---------|-----------|---------|---------|
| 仅口令保护 | 低（口令可绕过） | 低 | 好 | **短期** |
| 口令 + SQLCipher | 高（数据加密） | 中 | 好（透明） | **中期** |
| 口令 + VeraCrypt | 极高 | 低（外部工具） | 差（手动挂载） | 不推荐 |
| 口令 + SQLite SEE | 高 | 低（API 不变） | 好 | **长期（付费）** |

## 3. 推荐方案

### 短期（立即可落地）

**口令保护（bcrypt/argon2）**：
- 工作区创建时可选设置口令
- 口令哈希存储在配置中，切换工作区时验证
- 不加密数据本身，仅作为访问控制
- 实现简单，无依赖变更

### 中期（后续评估）

**SQLCipher 集成**：
- 将 SQLite 驱动从 `sqlite3` 替换为 `pysqlcipher3`
- 工作区口令作为 SQLCipher PRAGMA key
- 数据库文件级加密，口令正确才能打开数据库
- 向量数据（ChromaDB）单独评估加密方案（ChromaDB 不支持 SQLCipher）

### 长期（如有需求）

**SQLite SEE 评估**：
- 若预算允许，评估 SQLite SEE 替代 SQLCipher
- API 完全兼容，无需修改业务代码

## 4. 加密密钥丢失恢复流程

### 4.1 场景：主密钥丢失（字段级加密）

1. **确认丢失**：OS 密钥环中 `kvault/master_key` 不存在，且 `data/keys/master.key` 丢失
2. **影响范围**：所有加密字段无法解密（如标签、分区名等），文档原文和向量索引不受影响
3. **恢复步骤**：
   - 若有密钥备份：导入主密钥到密钥环或 `data/keys/master.key`
   - 若无密钥备份：
     a. 加密字段不可恢复，需手动重建（重新设置标签、分区名）
     b. 文档和向量索引可继续使用
     c. 生成新主密钥，重新标记并加密字段

### 4.2 场景：工作区口令遗忘

1. **确认遗忘**：口令哈希存在但无法匹配任何输入
2. **影响范围**：无法进入该工作区
3. **恢复步骤**：
   - **无后门**：口令哈希不可逆，无法恢复原口令
   - **数据恢复**：直接访问 `data/workspaces/<ws_id>/` 目录中的 SQLite 和 ChromaDB 文件（口令仅控制 GUI 访问，不加密数据）
   - **重置口令**：删除 `config.json` 中该工作区的 `password_hash` 字段，重新设置

### 4.3 场景：SQLCipher 密钥遗忘（中期方案）

1. **确认遗忘**：PRAGMA key 验证失败
2. **影响范围**：该工作区全部数据不可访问
3. **恢复步骤**：
   - **无后门**：SQLCipher 使用 AES-256 加密，密钥丢失则数据不可恢复
   - **预防**：强烈建议用户备份工作区口令到安全位置
   - **灾难恢复**：从备份恢复 `data/workspaces/<ws_id>/` 目录（备份时未加密）
