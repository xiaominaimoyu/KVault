# 对话历史与上下文压缩设计

> 本文档描述 KVault 检索会话的上下文管理、压缩策略及 MCP session 衔接方案。
> 本任务仅输出设计文档，不实现代码。

---

## 1. 会话状态流转

一次完整的检索-生成会话经历以下状态：

```
idle → querying → retrieving → generating → compressing → idle
```

| 状态 | 说明 | 触发条件 | 退出条件 |
|------|------|---------|---------|
| `idle` | 空闲，等待用户输入 | 会话初始化或上一轮处理完成 | 用户提交查询 |
| `querying` | 接收并校验用户查询 | 用户提交查询 | 查询校验通过 |
| `retrieving` | 执行向量/混合检索 | 查询校验通过 | 检索结果返回 |
| `generating` | 拼接上下文并调用 LLM 生成回答 | 检索结果非空 | 生成完成或失败 |
| `compressing` | 压缩会话上下文，淘汰旧轮次 | 上下文长度超过阈值 | 压缩完成 |
| `idle` | 回到空闲，保留压缩后的上下文 | 压缩完成 | 下一轮查询 |

### 状态流转图

```
┌──────┐  用户查询  ┌──────────┐  校验通过  ┌─────────────┐  检索完成  ┌────────────┐
│ idle │ ─────────→ │ querying │ ─────────→ │ retrieving  │ ─────────→ │ generating │
└──────┘            └──────────┘            └─────────────┘            └────────────┘
    ↑                                                                      │
    │                    上下文超阈值          ┌────────────┐  生成完成     │
    └────────────────────────────────────── │ compressing │ ←────────────┘
                                             └────────────┘
```

### 异常处理

- `querying` 阶段校验失败（空查询、超长输入）→ 直接回退到 `idle`，记录错误
- `retrieving` 阶段检索结果为空 → 跳过 `generating`，直接进入 `compressing`（或回退 `idle`）
- `generating` 阶段 LLM 调用失败 → 记录错误，保留已检索上下文，回退 `idle` 等待重试
- `compressing` 阶段压缩失败 → 保留未压缩上下文（降级为滑动窗口截断），回退 `idle`

## 2. 上下文压缩策略

随着对话轮次增加，累积的检索片段和生成回答会使上下文超出 LLM 上下文窗口限制。以下三种策略可组合使用。

### 2.1 摘要压缩（Summary Compression）

**机制**：当历史轮次超过 N 轮（默认 N=5）时，将最早的 K 轮对话（用户查询 + 检索片段 + 生成回答）调用 LLM 生成一段摘要文本，替换原始内容。

**适用场景**：
- 长对话（>10 轮），早期话题已充分讨论
- LLM 上下文窗口较小（如 4K token）
- 需要保留早期对话的语义要点而非逐字记录

**权衡**：
- 优点：大幅减少 token 占用，保留语义要点
- 缺点：摘要调用额外消耗 LLM 推理资源；摘要可能丢失细节；不可逆
- 建议：仅对超过阈值的最旧轮次执行，保留最近 N 轮原文

### 2.2 滑动窗口（Sliding Window）

**机制**：仅保留最近 W 轮对话的完整内容（默认 W=10），更早的轮次直接丢弃。

**适用场景**：
- 短期对话，用户关注最近几轮交互
- 无需 LLM 额外调用，零成本
- 作为摘要压缩的兜底策略

**权衡**：
- 优点：实现简单，无额外推理开销，确定性强
- 缺点：早期上下文完全丢失，可能丢失关键约束或偏好
- 建议：与摘要压缩组合——窗口外的轮次先尝试摘要，摘要失败则丢弃

### 2.3 关键片段保留（Key Fragment Retention）

**机制**：从历史检索片段中提取高相似度（score ≥ 阈值）的片段，标记为「关键片段」永久保留，不受滑动窗口淘汰影响。

**适用场景**：
- 用户反复追问同一文档的不同细节
- 需要跨轮次保持对特定文档片段的引用
- 检索结果中存在高置信度匹配

**权衡**：
- 优点：保证关键信息不丢失，检索质量稳定
- 缺点：关键片段过多时上下文仍可能超限；需要额外的标记管理
- 建议：设置关键片段上限（如 20 条），超出时按相似度淘汰最低分

### 2.4 组合策略推荐

```
压缩流程（上下文长度 > 阈值时触发）：
1. 保留所有「关键片段」标记的检索结果
2. 保留最近 W 轮完整对话（滑动窗口）
3. 窗口外的轮次尝试摘要压缩（调用 LLM）
4. 摘要失败或仍超限 → 丢弃最早轮次
5. 仍超限 → 截断单轮内的检索片段（保留 top_k 个）
```

## 3. MCP Session 衔接方案

### 3.1 Session 参数定义

MCP 工具新增可选参数 `session_id: Optional[str]`：

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `session_id` | `str` | 否 | 会话标识符。不传时视为无状态单次调用；传入时加载/保存会话上下文 |

`session_id` 由 MCP 客户端生成（建议使用 UUID v4），在同一对话线程内保持不变。

### 3.2 存储路径

会话上下文以 JSON 文件持久化到本地：

```
data/
└── sessions/
    ├── <session_id>.json     # 会话上下文文件
    └── ...
```

每个会话文件结构：

```json
{
  "session_id": "uuid-v4",
  "created_at": "2026-09-01T10:00:00Z",
  "updated_at": "2026-09-01T10:05:30Z",
  "state": "idle",
  "turns": [
    {
      "turn_id": 1,
      "query": "用户查询文本",
      "retrieved_fragments": [
        {"doc_id": "...", "chunk_id": "...", "content": "...", "score": 0.85, "is_key": true}
      ],
      "answer": "LLM 生成回答",
      "timestamp": "2026-09-01T10:00:05Z"
    }
  ],
  "summary": "早期轮次摘要（如有）",
  "key_fragments": [
    {"doc_id": "...", "chunk_id": "...", "content": "...", "score": 0.92}
  ]
}
```

### 3.3 MCP 工具行为变更

以 `search_knowledge_base` 为例：

- **不传 `session_id`**：行为与当前一致，无状态单次检索
- **传入 `session_id`**：
  1. 加载 `data/sessions/<session_id>.json`（不存在则创建）
  2. 执行检索，将本轮检索片段追加到 `turns[-1].retrieved_fragments`
  3. 标记高相似度片段为 `is_key`，追加到 `key_fragments`
  4. 若上下文长度超过阈值，触发压缩流程
  5. 保存会话文件，返回检索结果（附带 `session_id` 供客户端确认）

### 3.4 TTL 过期清理

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `session_ttl` | 7 天 | 会话文件过期时间 |
| `cleanup_interval` | 24 小时 | 清理任务执行间隔 |

清理逻辑：
1. 启动时及每 `cleanup_interval` 扫描 `data/sessions/`
2. 对每个 `.json` 文件，检查 `updated_at + session_ttl < now()`
3. 过期文件直接删除
4. 记录清理日志

配置项写入 `config.json` 的 `sessions` 段：

```json
{
  "sessions": {
    "enabled": true,
    "session_ttl_days": 7,
    "cleanup_interval_hours": 24,
    "compression_threshold_tokens": 3000,
    "sliding_window_turns": 10,
    "summary_threshold_turns": 5,
    "key_fragment_score_threshold": 0.8,
    "max_key_fragments": 20
  }
}
```

## 4. 权衡说明

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 会话存储格式 | JSON 文件（非 SQLite） | 会话数据量小，JSON 便于调试与人工检查；避免与元数据库耦合 |
| 压缩触发时机 | 按轮次 + token 阈值双触发 | 单纯按轮次可能在长回答时仍超限，token 阈值作为硬保障 |
| 摘要压缩调用 | 复用已有 Ollama LLM | 不引入额外依赖；用户已配置的生成模型可直接用于摘要 |
| 关键片段上限 | 20 条 | 平衡保留率与上下文占用；可配置 |
| Session 清理 | 被动扫描（非定时线程） | 桌面应用无需常驻后台线程；在启动和检索时触发清理即可 |
| `session_id` 生成 | 客户端生成 | MCP 服务端无状态更简单；客户端掌握会话生命周期 |
| 无 `session_id` 时行为 | 完全无状态（向后兼容） | 不破坏现有 MCP 调用方；渐进式启用会话功能 |

### 与现有架构的关系

- **不改动** `core/retriever.py` 检索逻辑——会话层在检索之上
- **不改动** `core/vector_store.py` / `core/metadata_manager.py`——会话数据独立于索引数据
- **未来实现时**新增 `core/session_manager.py` 管理会话状态与压缩
- **未来实现时**修改 `mcp_server/tools.py` 增加 `session_id` 参数透传
- GUI 侧对话功能（如有）通过 `SessionManager` 管理本地会话，不依赖 MCP session
